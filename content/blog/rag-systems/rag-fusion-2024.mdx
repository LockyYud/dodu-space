## Thesis

RAG-Fusion đáng học như một pattern, không phải như một paper claim. Ý tưởng thực dụng là: **nếu một query duy nhất quá giòn, hãy tạo nhiều cách hỏi và hợp nhất kết quả bằng rank fusion**.

Tôi sẽ dùng nó như một recall booster có kiểm soát, không dùng như default cho mọi request.

## Problem I Care About

Single-query retrieval dễ fail vì user query chỉ là một lát cắt của intent.

```text
"làm sao giảm hallucination trong RAG?"
```

Query này có thể cần documents về:

- retrieval quality;
- citation faithfulness;
- abstention;
- answer verification;
- query rewriting;
- context filtering.

Một embedding vector duy nhất có thể kéo retrieval về một hướng quá hẹp. RAG-Fusion cố gắng mở rộng query space trước khi retrieve.

## The Pattern

Pipeline:

```text
original query
  -> generate N rewritten queries
  -> retrieve top-k for each query
  -> merge ranked lists with RRF
  -> use fused results as context candidates
```

RRF score:

```text
score(d) = sum(1 / (k + rank_i(d)))
```

RRF hữu ích vì không cần normalize score giữa các retrieval runs. Một document xuất hiện ổn định trong nhiều ranked lists sẽ được đẩy lên.

## What Actually Matters

RAG-Fusion chỉ có giá trị nếu generated queries thật sự khác nhau.

Nếu LLM tạo 4 câu paraphrase gần giống nhau, retrieval lists sẽ overlap mạnh. Khi đó RRF chỉ reweight lại cùng một tập documents, gần như không tăng recall.

Điểm cần monitor không phải chỉ là answer quality, mà còn:

- diversity giữa rewritten queries;
- overlap giữa top-k result sets;
- số document mới được thêm nhờ fusion;
- tỷ lệ query variants gây drift khỏi intent gốc.

## Implementation Sketch

Version tôi sẽ implement:

```text
1. Generate 3 query variants:
   - paraphrase semantic;
   - keyword-oriented;
   - sub-aspect query.

2. Retrieve bằng hybrid search cho mỗi query.

3. Merge tất cả ranked lists bằng RRF.

4. Rerank fused top candidates.

5. Log:
   - generated queries;
   - overlap matrix;
   - final selected chunks;
   - answer citations.
```

Tôi sẽ giữ số variants nhỏ, thường 3-4. Nhiều hơn dễ tăng latency và noise nhanh hơn tăng recall.

## Production Tradeoffs

**Latency tăng tuyến tính** nếu retrieval không parallel. Với hybrid retrieval, N query variants có thể nhân đôi hoặc nhân ba số calls.

**Query drift** là rủi ro lớn. Variant có thể mở rộng intent quá mức và kéo documents không liên quan vào context.

**Diminishing returns** đến nhanh. Sau vài variants đầu, LLM thường sinh câu hỏi lặp hoặc quá rộng.

**Fusion không thay thế reranking**. RRF tăng candidates tốt hơn, nhưng final precision vẫn cần reranker hoặc relevance filter.

## When I Would Use It

Tôi sẽ dùng RAG-Fusion khi:

- user query mơ hồ nhưng không nên hỏi lại;
- câu hỏi có nhiều khía cạnh;
- corpus dùng nhiều vocabulary khác nhau;
- baseline retrieval có recall thấp;
- latency budget cho phép parallel retrieval.

Nó đặc biệt hợp với research assistant, knowledge base rộng, và exploratory QA.

## When I Would Not Use It

Tôi sẽ không dùng cho:

- exact lookup;
- query có mã định danh;
- realtime chat latency thấp;
- corpus nhỏ;
- task cần precision cao hơn recall.

Với exact query, query diversification có thể làm hỏng retrieval bằng cách làm mất token quan trọng.

## What I Distrust

Tôi không tin các con số improvement của RAG-Fusion nếu không có ablation rõ:

```text
single query
single query + reranker
multi-query without fusion
multi-query + RRF
multi-query + RRF + reranker
```

RAG-Fusion ban đầu cũng không phải peer-reviewed paper. Bằng chứng mạnh nhất trong stack này thực ra là RRF từ IR truyền thống, không phải toàn bộ recipe RAG-Fusion.

## Experiment I Would Run

Tôi sẽ chạy:

```text
N = 1, 2, 4, 8 query variants
```

Và đo:

- Recall@10;
- answer correctness;
- citation faithfulness;
- query diversity;
- top-k overlap;
- latency p95;
- cost/query;
- drift rate.

Tôi muốn tìm sweet spot theo corpus. Nếu N=4 tốt hơn N=8 về cost-quality, N=4 là default.

## Takeaway

RAG-Fusion là một recall technique tốt khi single-query retrieval quá giòn.

Điểm cần nhớ:

- giá trị nằm ở query diversity, không phải số query;
- RRF là cách merge đơn giản và bền;
- phải giữ original query làm anchor;
- cần reranker sau fusion;
- không dùng mặc định cho exact lookup hoặc latency-sensitive paths.
