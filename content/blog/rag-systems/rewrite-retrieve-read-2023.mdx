> **Paper**: Query Rewriting for Retrieval-Augmented Large Language Models
> **Tác giả**: Xinbei Ma, Yeyun Gong, Pengcheng He, Hai Zhao, Nan Duan
> **Venue**: EMNLP 2023 — arXiv:2305.14283
> **Loại**: `engineering_reading_note`

## Thesis

Query rewriting đáng học vì nó xem retrieval như một interface problem. User query không nhất thiết là search query tốt. Thay vì sửa retriever hoặc generator ngay, ta có thể thêm một adapter layer ở giữa: **rewrite query để nói đúng ngôn ngữ của corpus và retriever**.

Trong production RAG, đây thường là kỹ thuật rẻ hơn fine-tune retriever.

## Problem I Care About

User không viết query theo cách tài liệu được index.

```text
User: "sao bot trả lời bịa khi tài liệu thiếu?"
Docs: "hallucination under insufficient evidence"
```

Hoặc user hỏi quá dài:

```text
"Tôi đang dùng pipeline vector search với chunks khoảng 800 tokens,
nhưng khi hỏi về chính sách refund ở EU thì model trả lời rất mơ hồ,
không biết có phải do retrieval không?"
```

Retriever cần một query gọn hơn:

```text
"EU refund policy retrieval failure RAG"
```

Query rewriting xử lý khoảng cách này.

## The Paper's Core Idea

Paper chèn một trainable rewriter vào pipeline:

```text
input question -> rewriter -> rewritten query -> retriever -> reader
```

Rewriter được warm-up bằng supervised data, sau đó optimize bằng reinforcement learning với reader performance làm reward. Ý tưởng là rewriter không chỉ paraphrase đẹp hơn, mà học cách rewrite sao cho downstream QA tốt hơn.

Điểm quan trọng: retriever và reader có thể giữ nguyên. Rewriter là layer nhỏ hơn, dễ thay thế hơn.

## What Actually Matters

Bài học production là: **đừng coi query của user là bất khả xâm phạm ở retrieval step**.

Ta có thể biến query theo nhiều mục tiêu:

- normalize thuật ngữ;
- thêm synonym domain-specific;
- rút gọn câu hỏi dài;
- tách multi-intent query;
- thêm entity/context từ conversation;
- chuyển natural language thành keyword query;
- tạo nhiều query variants để tăng recall.

Nhưng rewriting cũng nguy hiểm: nếu rewriter tự thêm giả định sai, retriever sẽ đi lệch ngay từ đầu.

## Implementation Sketch

Tôi sẽ không bắt đầu bằng RL như paper. Version production tối giản hơn:

```text
1. Classify query type:
   - exact lookup;
   - semantic question;
   - multi-hop;
   - broad summary;
   - ambiguous.

2. Rewrite only when useful:
   - exact lookup: keep original;
   - semantic question: rewrite to search-friendly form;
   - broad summary: generate subqueries;
   - ambiguous: ask clarification or preserve original.

3. Retrieve with both original and rewritten query.

4. Fuse results with RRF.

5. Log original_query, rewritten_query, retrieved_docs, final answer.
```

Điểm tôi muốn giữ là **original query vẫn được retrieve**. Rewriter không nên có quyền phá toàn bộ retrieval.

## Production Tradeoffs

**Rewrite drift** là rủi ro chính. LLM có thể thêm entity, time range, hoặc constraint không có trong user query.

**Latency** tăng thêm một LLM call. Có thể giảm bằng small model, rules, cache, hoặc chỉ rewrite query dài/semantic.

**Eval khó hơn** vì rewrite thay đổi distribution. Nếu answer sai, cần debug: lỗi do original query, rewrite, retriever, reranker, hay generator?

**Conversation context** vừa hữu ích vừa nguy hiểm. Rewriter có thể resolve pronoun từ chat history, nhưng cũng có thể kéo nhầm context cũ vào query mới.

## When I Would Use It

Tôi sẽ dùng query rewriting khi:

- user query dài, tự nhiên, nhiều nhiễu;
- corpus dùng thuật ngữ khác user;
- retrieval recall thấp nhưng evidence có tồn tại;
- app có conversational context;
- cần query expansion nhẹ trước hybrid retrieval.

## When I Would Not Use It

Tôi sẽ tránh rewrite hoặc chỉ rewrite rất bảo thủ khi:

- query chứa mã, số hiệu, tên file, function name, error code;
- legal/medical wording cần giữ nguyên;
- user đang quote một câu cụ thể;
- rewriter chưa được log và eval;
- latency budget quá chặt.

Trong các case này, original query nên được ưu tiên.

## What I Distrust

Tôi không muốn copy training recipe RL từ paper trước khi có baseline đơn giản. RL reward từ reader performance có thể optimize theo metric nhưng làm query khó interpret hơn.

Tôi cũng không tin rewrite quality nếu chỉ nhìn rewritten query có vẻ "hay hơn". Query tốt là query retrieve được evidence tốt, không phải query đọc tự nhiên hơn.

## Experiment I Would Run

Tôi sẽ so:

```text
original only
rewrite only
original + rewrite via RRF
multi-query rewrite + RRF
query classifier + conditional rewrite
```

Metrics:

- Recall@k;
- answer correctness;
- rewrite drift rate;
- exact-token preservation;
- latency;
- cost;
- number of unnecessary rewrites.

Tôi cũng sẽ sample manual các rewritten queries và gắn nhãn:

```text
safe
useful expansion
too broad
lost constraint
added unsupported assumption
```

Nếu rewrite drift cao, rewrite phải chuyển sang conditional hoặc rule-constrained.

## Takeaway

Query rewriting là adapter layer tốt cho RAG, nhưng không nên là magic box.

Điểm cần nhớ:

- user query không luôn là retrieval query tốt;
- rewrite nên được eval bằng retrieval outcome;
- original query nên được giữ như safety anchor;
- exact lookup thường không nên rewrite;
- conditional rewrite thực dụng hơn rewrite mọi query.
