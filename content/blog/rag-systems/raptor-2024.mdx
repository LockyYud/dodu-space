> **Paper**: RAPTOR: Recursive Abstractive Processing for Tree-Organized Retrieval
> **Tác giả**: Parth Sarthi, Salman Abdullah, Aditi Sehrawat, Srividya Gollapalli, Anirudh Baggari, Christopher D. Manning
> **Venue**: ICLR 2024 — arXiv:2401.18059
> **Loại**: `engineering_reading_note`

## Thesis

RAPTOR đáng học vì nó chỉ ra giới hạn của flat chunk retrieval: **không phải câu hỏi nào cũng được trả lời tốt bằng vài chunks rời rạc**.

Nếu câu hỏi cần tổng hợp qua nhiều phần của một tài liệu dài, retrieval ở nhiều mức trừu tượng có thể tốt hơn retrieval chỉ ở leaf chunks.

## Problem I Care About

Flat RAG thường chia tài liệu thành chunks rồi retrieve top-k.

Điều này ổn với câu hỏi local:

```text
"Điều khoản termination nằm ở đâu?"
```

Nhưng kém với câu hỏi global hoặc synthesis:

```text
"Tài liệu này lập luận chính như thế nào?"
"Các nguyên nhân chính của incident là gì?"
"Feedback của khách hàng xoay quanh những theme nào?"
```

Top-k chunks có thể lấy được các mảnh liên quan, nhưng thiếu tầng summary để kết nối chúng.

## The Paper's Core Idea

RAPTOR xây một tree index:

```text
leaf chunks
  -> cluster semantically related chunks
  -> summarize each cluster
  -> embed summaries
  -> repeat recursively
```

Khi query, hệ thống có thể retrieve cả leaf chunks lẫn summary nodes. Nhờ vậy, context có thể chứa thông tin chi tiết và thông tin tổng quan.

## What Actually Matters

Bài học quan trọng là **retrieval granularity phải khớp với query granularity**.

Một query hỏi chi tiết cần leaf chunk. Một query hỏi theme cần summary node. Một query hỏi so sánh có thể cần cả hai.

Flat chunking ép mọi câu hỏi vào cùng một mức granularity. RAPTOR mở thêm tầng retrieval.

## Implementation Sketch

Version tối giản tôi sẽ build:

```text
Indexing:
1. Chunk documents thành leaf nodes.
2. Embed leaf nodes.
3. Cluster chunks theo document hoặc section trước, semantic sau.
4. Generate summary cho mỗi cluster.
5. Embed summary nodes.
6. Lặp 1-2 tầng, không xây cây quá sâu.

Query:
1. Classify query as local vs global vs mixed.
2. Local: retrieve leaf chunks.
3. Global: retrieve summary nodes first.
4. Mixed: retrieve summary nodes + supporting leaf chunks.
5. Rerank and pack context.
```

Tôi sẽ ưu tiên traceability: mỗi summary node phải link về child chunks.

## Production Tradeoffs

**Indexing cost cao** vì phải summarize nhiều clusters bằng LLM.

**Summary hallucination** là rủi ro thật. Nếu summary node bịa hoặc bỏ sót, retrieval tầng trên sẽ dẫn generator đi sai.

**Incremental updates khó**. Thêm tài liệu mới có thể cần rebuild clusters/summaries.

**Debug phức tạp hơn flat retrieval**. Khi answer sai, cần biết lỗi nằm ở chunking, clustering, summary, retrieval, hay generation.

## When I Would Use It

Tôi sẽ dùng RAPTOR-like indexing khi:

- tài liệu dài;
- query thường hỏi tổng quan, theme, synthesis;
- corpus tương đối ổn định;
- latency query quan trọng hơn cost indexing;
- cần context cô đọng hơn top-k chunks.

## When I Would Not Use It

Tôi sẽ không dùng khi:

- corpus thay đổi liên tục;
- câu hỏi chủ yếu là exact lookup;
- tài liệu ngắn;
- chưa có eval cho summary quality;
- team chưa vận hành được flat hybrid retrieval tốt.

RAPTOR là tầng nâng cấp, không phải baseline đầu tiên.

## What I Distrust

Tôi không tin summary nodes nếu không có audit trail. Summary là generated content, không phải source of truth. Nếu dùng summary làm context, citation cuối cùng vẫn nên trỏ về source chunks.

Tôi cũng nghi ngờ clustering hoàn toàn semantic trên corpus nhiều domain. Có lúc structure sẵn có của tài liệu như heading, section, page, ticket thread đáng tin hơn embedding clustering.

## Experiment I Would Run

Tôi sẽ tạo eval chia theo query granularity:

```text
local fact
section-level synthesis
document-level summary
cross-section comparison
```

So:

```text
flat hybrid retrieval
parent-child retrieval
RAPTOR leaf-only
RAPTOR summary-only
RAPTOR mixed retrieval
```

Metrics:

- answer correctness;
- citation support;
- summary faithfulness;
- context token count;
- indexing cost;
- update cost.

Nếu RAPTOR chỉ thắng global queries, router nên gọi nó có điều kiện.

## Takeaway

RAPTOR là lời nhắc rằng chunk không phải đơn vị retrieval duy nhất.

Điểm cần nhớ:

- query local cần chunk;
- query global cần summary;
- summary phải trace được về source;
- indexing cost và update cost là vấn đề lớn;
- nên route theo query type thay vì dùng hierarchical retrieval cho mọi thứ.
